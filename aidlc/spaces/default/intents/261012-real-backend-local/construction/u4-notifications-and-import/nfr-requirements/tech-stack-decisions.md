# Technology Decisions: U4 Notifications and Excel import

Existing stack kept (Next.js 16, React, strict TypeScript, Node 24, Vitest, Node test runner, Playwright, ESLint, Prettier) with U1's local stack, U2's identity and U3's directory and coordination functions. Source: the functional design and the answers in `nfr-requirements-questions.md`.

| ID | Decision | Rationale | Check |
|---|---|---|---|
| NFR2.18 | Tables, policies and the named functions are plain SQL migrations applied by U1's runner, with `SET search_path FROM CURRENT` and privilege revokes, like U1 to U3 | One mechanism | Migration repeatability test (NFR6.17) |
| NFR2.19 | One small read-only xlsx library, chosen at code generation as an exactly pinned version: read-only, no formula evaluation, maintained, minimal dependencies, passes the dependency audit; the choice and the alternatives considered are recorded in the code summary; the parser runs in a server-only module and reads the bytes of the upload | Smallest attack surface for hostile files (NFR1.48, NFR1.49) | Dependency audit, the parser tests of NFR1.48 and a bundle scan proving the library is absent from client output |
| NFR2.20 | The import file reaches the server as a server-action upload (bytes); the Next.js server-action body limit is one application-wide setting (`serverActions.bodySizeLimit` in `next.config.ts`, none today), raised to 6 MB; the cost is that other server actions also accept up to 6 MB of body, which is accepted because they carry only small forms, and the import action itself enforces the 5 MB file limit with a Hungarian message (BR41.2) | The 5 MB limit needs a larger body limit than the 1 MB default | A browser or action test with a file just under 5 MB (accepted) and one over 6 MB (rejected with a Hungarian message, not a framework error) |
| NFR2.21 | Matching, classification, staging, conflict handling and commit are database functions that take the parsed rows as data; parsing and the checks that need the file (BR41.2) happen in the server module before the database call | Keeps the atomic commit in the database and the file handling in one place | Contract tests of the adapter against the real stack; atomicity tests (NFR6.19) |
| NFR2.22 | The reminder tick is a database function called lazily by the server (notification list, reminders screen), the seed and housekeeping; no scheduler or new service is added | Local environment, simulated delivery | Idempotent and concurrent tick tests (NFR6.22) |
| NFR2.23 | The notification and import adapters live in `src/data/` beside U3's, use U1's database client wrapper and map results once (U3 BR32.4, BR42.3) | Same pattern; screens stay on the same facades | Adapter fake tests and the code-by-code contract test (NFR2.26) |
| NFR2.24 | The fictitious workbook is generated from the template in the design by a test helper (the xlsx library or a minimal writer in test code), never read from `source-materials/` | NFR1.50 | A path-guard test that no test or code reads `source-materials/` (NFR1.50) |
| NFR2.25 | Checks before the unit completes: strict type check, lint, format check, all tests, production build, start smoke, the critical browser flows with the accessibility scan, secret and privacy scans, dependency audit (high and critical block), and at least 80% line, branch and function coverage across all production source, measured after the old `src/notifications` and `src/import-migration` modules are deleted | Team practice and NFR2 | The verification chain of the unit |
| NFR2.26 | These proofs run on every build and block the unit: the code-by-code contract test for the result codes (BR42.3), the hand-off completeness test (BR42.5), and the rule that an old module is deleted only when every one of its ledger rows has a proof (BR43.1) | Makes the carry-over rules enforceable | The named tests run in CI and block the unit |
| NFR2.27 | Lint and format scope: every folder U4 adds source in is added to the `lint`, `format` and `format:check` lists in `package.json` (the parser module `src/import-parser/` and the adapters already in `src/data/`), and U3's scope-guard test (`scripts/verification/lint-scope.test.ts`) fails if a source folder is outside the scope; the deleted `src/notifications` and `src/import-migration` leave its legacy allow-list | The most security-sensitive new code (hostile workbooks) is linted and formatted | The scope-guard test |
| NFR8.3 | Identifiers, schema names, functions, logs and technical documents are English; all screen text is Hungarian | NFR8 | Review of the change; the existing English-identifier and Hungarian-copy checks |

Numbering: ids in this unit are scoped to this unit's directory; U1 to U3 have their own with the same prefixes.
