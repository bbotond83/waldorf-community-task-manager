# Reliability Requirements: U4 Notifications and Excel import

Source: NFR6 and NFR2 of the requirements, rules BR40.1, BR40.6, BR41.6, BR41.8, BR41.9, BR42.1, BR42.3.

| ID | Requirement | Check |
|---|---|---|
| NFR6.17 | U4's migrations apply cleanly on a fresh database and a second time (forward-only), in the default and a worker schema; merged migrations are never edited | The migration repeatability test is extended to U4's files |
| NFR6.18 | Every use case is one transaction: after any injected failure nothing of it is stored, including the notices of the U3 use cases (a failed notice write rolls the use case back, BR40.1) | Failure-injection tests per use case |
| NFR6.19 | An interrupted import commit leaves the data exactly as it was and the run recoverable: a failing row set (database) and an injected client error (adapter) prove the data is unchanged; `import_mark_interrupted` failing too leaves the run committable again (BR41.9) | Atomicity and recovery tests |
| NFR6.20 | A repeated call with the same idempotency key returns the stored result and changes nothing more for commit, resolve and retry; a fresh key per attempt is generated by the adapter (BR42.1) | Repeated-key and reused-key tests |
| NFR6.21 | Stale versions never overwrite: conflict resolution, reminder retry and commit return the stored codes (IMPORT_PREVIEW_STALE, REMINDER_STALE, IMPORT_MATCH_CHANGED) | A stale-version test per operation |
| NFR6.22 | The reminder tick is idempotent and safe to run any time and concurrently: one attempt per due job, no duplicate notices (BR40.6) | Repeated and concurrent tick tests |
| NFR6.23 | The database unreachable, a timeout or a deadlock maps to the retryable failure, anything unknown to the terminal failure, and no database text reaches a screen (U3 BR32.4) | Tests with an injected database error at the adapter boundary |
| NFR6.24 | The interim port of U3 is removed from the production path and the notification page of a real parent works with real data; the synthetic composition is unchanged (BR42.1) | Wiring test and a browser test for a real parent |
| NFR6.26 | An import commit creates no Notification rows for the assignments it creates (a burst of sign-up confirmations would be noise) and does plan the reminder jobs and recipients for them (owner-confirmed decision, `nfr-requirements-questions.md` assumption 6); the design's BR40.9 table has no import row because import-created assignments are written by the commit, not by the sign-up use cases | The commit database test counts Notification rows (zero for imported assignments) and reminder jobs (present) |
| NFR6.25 | A hand-off completeness test runs every entry of `NOTIFICATION_USE_CASES` and the extra functions and checks the notice and job behaviour of the BR40.9 table (BR42.5) | The database test and the unit test of the list |

Availability targets (SLA, SLO) do not apply: the environment is local.
