## Deviations from the design and decisions to confirm

1. **Amendment A (task rows may refer to groups and families created by the same file).** The design matched a task row's group and family against existing data only, so a first import into an empty or partly filled organization turned every task row into a conflict. Directory rows are now decided first and task rows may name a group or family the same workbook creates; unknown references that nobody creates stay conflicts. The commit applies directory rows before task rows in one transaction. Proof: `import-functions.test.ts` (Amendment A) and `import-commit.test.ts` (first import).
2. **Wrappers `*_core` for U3 functions.** To add the notice and job writes without touching U3's tested bodies, each hooked function (`duty_sign_up`, `assignment_assign`, `assignment_remove`, `swap_request`, `swap_respond`, `coordination_decide` behind `swap_decide` and `cancellation_decide`, `family_archive`, `task_save`, `event_save`, `settings_save`, `lifecycle_run`: 11 cores) is renamed to `<name>_core` and a function with the old name and signature calls it and then writes the notices and re-plans the reminders, in the same transaction, only for a fresh success (not for a refusal or a replayed stored result). `swap_withdraw`, `cancellation_request` and `family_restore` are not wrapped: the table has no behaviour for them, and a test proves they create nothing. The cores are internal; no application role may execute them. The import commit calls the cores directly so imported places write no parent notices (NFR6.26).
3. **`reminder_run_due` and `reminder_run_due_system`.** The tick is split in two functions: an organization member ticks their own organization; the system caller (seed, reset, housekeeping) uses the `_system` function that takes the organization as an argument. Neither accepts the service-role key for table access.
4. **Import library `@e965/xlsx` 0.20.3 (exactly pinned).** It is the npm republish of SheetJS Community Edition 0.20.x (package description "SheetJS Spreadsheet data parser and writer", repository `e965/sheetjs-npm-publisher`, licence Apache-2.0). It is used only as a cell reader: no formula is evaluated, formula cells are refused, nothing is read from a path, and only `src/import-parser/workbook.ts` imports it (a test checks that, and the bundle test proves it is not in the browser output). Alternatives that Step 2 weighed, as far as I can reconstruct them: the original `xlsx` package on npm (stopped at 0.18.5 with published advisories, not updated on npm any more, which is why the republish exists), `exceljs` (much larger, many dependencies, aimed at writing), `read-excel-file` (small, but does not expose the formula and cell-type information the cell-safety check needs). **The Step 2 note itself is not on disk in a place I could read; the owner may want to confirm this reasoning.** `npm audit` has no high or critical finding.
5. **Next.js 16.4.0 to 16.4.2 (with `@next/env`).** Bumped in an earlier batch of this unit. The reason is not written in any file I could read; the dependency audit is clean on 16.4.2. The application-wide server-action body limit is now 6 MB (`experimental.serverActions.bodySizeLimit`), so every other server action also accepts a body up to 6 MB (accepted in NFR2.20). The upload action itself refuses a file over 5 MB with a Hungarian message (the browser test sends 5.5 MB to prove the limit setting works end to end).
6. **Cell safety scope.** The nine archive sheets are only counted: their content is never read into the staged data, so it is not judged (a formula or an `=` text on an archive sheet does not refuse the workbook). The checks (formula, over 10000 characters, `=`, `+`, `@` at the start) apply to the eight interactive sheets, with the phone column exempt from the prefix rule.
7. **Lazy tick on failure.** The tick runs when a parent opens the notification list and when an admin opens the reminders list. If the tick itself fails (lost connection, denied caller), the list is still read as it is and the next opening ticks again; a failed tick never hides the list and never invents a state.
8. **Extra columns and conflict texts beyond `entities.md`.** `import_rows.warning_count`, `import_runs.changed_summary`, and on staged rows `unit_ref`, `is_leader`, `match_class`, `conflict_message`, `row_conflict` (what the preview decided; the commit compares it with its own second matching and is deleted with the staged row). The closed conflict-text list is: "Több egyező család.", "Az elem már létezik.", "Ismétlődő sor a fájlban.", "Ismeretlen csoport.", "Ismeretlen család.", "Hibás adat a sorban.", "Több egyező feladat.", "Az elem megváltozott." (the last two are additions: several matching tasks, and the commit's re-match found a unit changed since the preview).
9. **`dashboard_import_conflicts` counts only the asking super admin's runs** (open conflicts of previewed, confirmed or interrupted runs). A run belongs to the admin who started it, and a count of another admin's open conflicts would reveal that the run exists. Other callers see zero. U3's marker test was inverted.
10. **First import behaviour.** The first import into an empty organization works through Amendment A. A second upload by the same admin cancels the first open run and deletes its staged rows. After a finished run the result stays on screen with the "Új feltöltés" link.
11. **Known limit: recipients re-plan only on the BR40.9 events (corrected in the repair pass; the earlier text said "or when the tick runs", which is wrong: `reminder_run_jobs` never calls the planner).** A job's recipient families are recalculated by the planner only when one of the BR40.9 events runs: a use case of the hand-off table, a task, event or setting save, a family archive, the lifecycle. Nothing re-plans on a timer, and the tick only cancels or stales jobs whose task changed. Under the recipient scope `group` this has a visible effect: a family that **leaves a group through `directory_save` (membership ended) stays an active recipient of that group's open tasks and keeps getting the "Holnap: ..." notices, and a family that joins a group gets none**, until an unrelated event re-plans that task (a sign-up, a task save, a settings save). Under the scope `duty` (the default) membership does not matter, so the limit does not arise. A family that is archived or goes through the lifecycle is handled (it is removed at once). Why it is not fixed here: the fix is a `directory_save` wrapper that re-plans the group's open tasks, and the import commit applies families through the same function while it already holds task locks, so the fix has to reorder the commit's lock set (families, then every open task of the groups it names, ascending) to avoid reintroducing the deadlock of the first review finding; that is a change to `import_apply` that deserves its own review. **Owner decision:** fix it as a separate small piece, or accept the limit while the scope stays `duty`. Event notices share the existing list's timing label and simulated-provider line (a cosmetic limit recorded in BR40.2).
12. **Placeholder-drop deadlock: cause and fix.** The drop file of U3's placeholder tables (`20261035_placeholder_drop.sql`) reads the catalogue (policies and views) of every schema before it filters to its own, which takes read locks on tables in other schemas. Another test file truncating its own schema at the same moment could deadlock with it, which caused one failed run of the full directory suite. Fix (test code only): `tests/database/placeholder-drop.test.ts` takes the locks of all test schemas in sorted order and runs alone. No migration was changed.
13. **Hungarian titles of the notices are to be checked by the owner.** `notification_list` builds them from the kind and the task title: "Jelentkezés megerősítve: …", "Cserekérés érkezett: …", "Csere jóváhagyva: …", "Csere elutasítva: …", "Csere döntés: …", "Lemondás jóváhagyva: …", "Lemondás elutasítva: …", "Lemondás döntés: …", "A helyed törölve: …", "Egy hét múlva: …", "Holnap: …". The reminders list shows "<task> — 7 napos" or "<task> — 24 órás".
14. **Step 23 to 28 decisions (this batch).**
    - *Cancel control.* The existing screen had no way out of an open run (the upload form only shows when there is no run), so a wrong file would have waited for the seven-day expiry. The screen therefore offers "Import megszakítása" for an open run in production mode, calling `import.cancel` through a new `cancelImportAction`. It deletes the staged rows. Because the status never returns a cancelled run, the screen then shows the upload form, or the earlier finished run with its "Új feltöltés" link if there is one.
    - *"New upload" link.* The link is `/admin/import?uj=<run id>` and only holds while that finished run is the latest one. A first version used a fixed `?uj=1`; the browser test found that the screen then kept showing the upload form after the new upload (and after its commit). The run id in the address fixes that.
    - *Result counts.* The preview model gained optional `importedRows` and `skippedRows` (read from the run), because the result panel is drawn from the stored run after the page refreshes. The panel says how many elements were created or updated and how many rows stayed unchanged or were counted as archive rows. The confirmation states the real number of workbook rows and resolved conflicts. A conflict that can only be kept (nothing to import into) offers only "Meglévő adat megtartása".
    - *Interrupted run.* In production mode an interrupted run shows the recovery form and not the commit form (the database refuses a plain commit of an interrupted run).
    - *Messages.* The Hungarian table moved to `app/admin/_lib/import-messages.ts` (a "use server" file may only export actions) and gained IMPORT_CONFIRMATION_REQUIRED, IMPORT_RECOVERY_NOT_AVAILABLE and IMPORT_RECOVERY_ACTION_INVALID next to IMPORT_UNSAFE_CELL and IMPORT_MATCH_CHANGED.
    - *Bundle scan.* `tests/database/identity-bundle.test.ts` gained a test that the spreadsheet library's texts and the parser's codes are in no browser file and are in the server output (it found nothing in the client output).
    - *Eyebrow text.* The import page still says "Adminisztráció · szintetikus folyamat" in production mode (the owner-approved change list did not include it). It is now inaccurate for a real import: **owner decision.**
    - *NFR1.58, NFR1.59.* As in U3 (NFR1.38, NFR1.35), the application has no logging layer: failures are mapped to fixed-word errors and Hungarian messages and no database text travels, which the adapter tests prove; the "event code logged once at the adapter boundary" part is not implemented. Traceability points these two rows at the error-mapping tests.
