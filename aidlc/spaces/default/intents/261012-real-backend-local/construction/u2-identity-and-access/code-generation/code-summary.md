## Spike findings (step 1) and fallbacks

1. Key names confirmed: `[auth.sessions] inactivity_timeout = "720h"` (reaches the container as `GOTRUE_SESSIONS_INACTIVITY_TIMEOUT=720h0m0s`), `[auth.email] otp_expiry = 3600`, `max_frequency = "1m0s"`, `[auth.rate_limit] token_refresh / sign_in_sign_ups / token_verifications = 30`, template `content_path`. The 30-day inactivity timeout can be set; GoTrue enforces it at refresh, and `current_session_is_active()` also enforces it (stated fallback kept as defence in depth, tested).
2. Mail catcher: web 54324; its SMTP port is not published by default. `[local_smtp] smtp_port = 54325` publishes it (all interfaces, like the other ports; added to the exposure check).
3. **Sign-up switches (fallback applied):** `[auth.email] enable_signup = false` switches off the whole email provider (password sign-in and recovery answer `email_provider_disabled`). It stays `true`; `[auth] enable_signup = false` (`GOTRUE_DISABLE_SIGNUP=true`) refuses open sign-up (real call: 422 `signup_disabled`; admin create still works). Commented in the file and read back by a test.
4. **`email_sent` rate limit (fallback recorded):** the CLI does not forward it locally (container keeps its own `360000`); the file value 30 is kept and a test fails if the CLI starts forwarding something else. Mail only reaches the local catcher.
5. Finding for NFR1.24 (superseded, see "Review follow-up"): 45 consecutive password sign-ins in seconds were never rate limited by the sign-in service itself (the configured limits applied to refresh, OTP and verify settings), so the first version of this unit relied on the app lockout alone.
6. GoTrue mails a recovery link to a banned (deactivated) user, so the server asks `account_recovery_check` first.

## Review follow-up (review-01, owner decision on finding 2)

1. **Compensation safety (R-01).** `acceptInvitation` deletes a new sign-in user only after the release of its own reservation succeeded (`released`), which proves the acceptance never committed. If the release or the lookup is unavailable or says anything else, the user is kept, `follow_up_failed` (`delete_user_unproven`) is written, and the next submit reuses it (housekeeping removes it after an hour if it never gets an Account). The operator command deletes the new user only when a fresh connection answers that no Account exists for its id; a dropped connection after the commit, or a failing check, keeps the user and names it. Tests: lookup/release unavailable after a failed accept, accept committed but the answer lost (real stack), dropped connection after commit and a blind existence check in the operator command (fake and real stack).
2. **Brute force closed in the database (R-02, owner decision).** `[auth.hook.password_verification_attempt]` is registered (CLI 2.120.0 accepts it; the container receives `GOTRUE_HOOK_PASSWORD_VERIFICATION_ATTEMPT_*`) and points at `pg-functions://postgres/public/password_verification_hook` (migration `20261020_identity_password_hook.sql`). The security-definer function is executable only by `supabase_auth_admin` (the sign-in service's database role), counts per account under an advisory lock, rejects after 5 wrong passwords in 15 minutes counted from the fifth (even for the right password), does not record while locked, clears on success, and returns the generic rejection. It uses the same `sign_in_attempts` table with a SHA-256 key of the account id; `sign_in_attempt_clear` takes an optional user id so sign-in success and a password reset clear it too. The app screen keeps its own email-keyed lockout (covers unknown addresses, which never reach the hook) and its Hungarian messages. Real-stack tests: six direct calls lock, the sixth with the right password is refused, no extension while locked, 14 parallel wrong attempts record exactly 5, the 16-minute clock, accounts apart, privileges. The hook can name one schema, so only the default schema is wired (worker schemas hold the function for their own tests); this supersedes the "considered and declined" hook note of BR2.3 and the **NFR1.24 accepted-risk text** (the 360 guesses per hour figure was wrong: the service had no limit on password sign-ins). What is and is not configured now: configured are `minimum_password_length = 8` and `password_requirements = "letters_digits"` (the service enforces letter and digit itself; tested), the lockout hook, rate limits for refresh, OTP and verify (30 per 5 minutes per address) and the email gap. **Not configured:** any common-password or leaked-password check (the earlier claim of a common-password check was wrong; the CLI offers none for the local stack), per-address limits on password sign-in, CAPTCHA. The local stack still publishes its ports on all interfaces; the gate "no hosted or LAN-exposed use without the acknowledged firewall rule" stands, and the stack is meant to be reachable on loopback only.
3. **Reset-request timing (R-03).** `requestPasswordReset` takes a `defer` function; the action passes Next's `after()`, so the check and the mail run after the answer and the response time is independent of the address. Real-stack test: unknown, deactivated and active addresses answered in 0.2 to 0.6 ms (spread under 1 ms, target 100 ms), and the deferred mail still arrives only for the active one.
4. **Per-request refresh (R-04).** `src/identity/refresh.ts` and `proxy.ts`: on a page request with a refresh cookie and a missing or soon-expiring access token the proxy exchanges the pair once, passes the new cookies to the page of the same request and sets them in the browser (httpOnly, sameSite lax, secure over https, 30 days); a refusal (revoked, ended, idle past 30 days) clears the cookies; an unreachable service changes nothing. Requests without a session cookie take the old synchronous path. Tests: unit (fakes), proxy tests, real stack (renew an hour later, repeat renewals, revoked session, 31 days idle refused by both the service and the database) and a browser test with an expired access cookie. BR2.5 and BR2.7 now hold for pages as well as actions.
5. **Reservation identity (R-05).** `invitation_release(p_invitation_id, p_reserved_at)` releases only the reservation whose time the caller got from `invitation_reserve`; test: a stale first holder cannot release the second submit's reservation.
6. **Elevated list additions (not in the frozen functional-spec):** `invitation_release(uuid, timestamptz)`, `account_recovery_check(text)` and `sign_in_attempt_clear(text, uuid)` (admin access, service role); `password_verification_hook(jsonb)` (executable only by `supabase_auth_admin`); the catalogue test lists all of them.
7. **Handoff lists for later units.** (a) Scope probe record types still to register by their units: parent, task, event, change request, notification; the catalogue test fails when a table has no probe decision. (b) Group scope is not validated in `invitation_create` and `grant_change` (no group table yet): U3 must check the group against Directory's table. (c) `accounts.email` is not kept in step with a direct email change at the sign-in service (auto-confirm is on locally); not exercised, to be disabled or synchronised in U3/U5. (d) Pages never refresh tokens themselves; the proxy does, and any new server-side session reader must use the cookies after the proxy.
8. **Corrected commands** (the approved `unit-test-instructions.md` is unchanged and still names the old ones): screen tests `npx vitest run --config vitest.config.ts tests/integration/identity-screens.test.tsx` (plus `identity-actions`, `identity-runtime`, `identity-proxy`), database tests `npm run test:database:identity`, bundle check `npm run test:bundle`, server modules `node --experimental-strip-types --test src/identity/*.test.ts`.

Handoff note 7(c) above is closed by Major 2. A later unit that must change a sign-in email (an admin correcting an address) sets `app.identity_email_change` in a transaction and keeps `accounts.email` in step; the sign-in service does not set it (it sends plain updates), so its self-service route stays closed. This is behaviour, not a privilege: any role that can run SQL against the database can set the setting, which is the same trust level as dropping the trigger. The guard stops the sign-in service's own routes, not someone with direct database access. (The comment in `20261022_identity_email_change_guard.sql` says "cannot set it"; a merged migration is not edited, so this note is the correction.)

Design statements the repair changes (recorded here; the frozen design files are unchanged): `account_recovery_check(text)`, `invitation_release_stale()`, `identity_block_email_change()` and `identity_ban_mismatches()` belong on the elevated function list (admin access, internal, trigger and admin access respectively; the catalogue test lists them); reactivation lifts the sign-in ban through the admin access and the reconcile repeats it; the lock is five failed attempts inside a sliding 15-minute window, locked for 15 minutes from the fifth; `[auth.email] enable_signup` stays `true` (false turns the email provider off) and `supabase/config.toml` (`smtp_port = 54325`) is the one source of the SMTP port.

### Follow-up to the second code review (2026-10-21)

The second review of this unit found all eight earlier findings fixed and raised three Minor points, handled on `fix/u2-minor-points`:

1. **Reset after a spent link.** When the new password could not be set because the sign-in service was unavailable or rate limiting, or when ending the other sign-ins failed after the password had changed, the answer was generic "try again" advice, and resubmitting the same link only said "not valid". There are now two explicit outcomes with Hungarian messages: `RESET_LINK_SPENT` ("request a new link", with the link to do so) and `RESET_SESSIONS_NOT_ENDED` ("the password changed, sign in with it"). Tests: `reset.test.ts`, `form-state.test.ts`. In the second case the account's other sign-ins stay open until their normal expiry (30 days idle), because nothing retries the removal; this is a known limit that was already there, now stated. The person is told to sign in, and the failure is logged as `follow_up_failed`.
2. **Email-change guard wording.** Corrected above: the bypass setting is not protected by a privilege.
3. **Test instructions.** The reference to a plan step number was removed.
