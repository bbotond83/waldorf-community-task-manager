### Summary

The identity foundation is architecturally sound at the database level: the session check closes the direct-token bypass, the privileged functions are pinned, caller-checked and narrowly granted, and the key stays server-only. The unit is NOT-READY because four Major gaps remain: a failure path can delete a sign-in user that has an Account, the accepted brute-force risk rests on false numbers and a missing common-password check, the reset request leaks account existence by timing, and the per-request session refresh promised by the spec is not built. On the developer's questions: the accepted-risk wording is wider than assumed and needs a server-side limit or a fresh owner decision before any use beyond loopback; no deviation (own cookie module, two extra admin functions, narrowed probe, landing page) is a blocker by itself, but the extra functions and the instruction command must be written back into the approved documents.
