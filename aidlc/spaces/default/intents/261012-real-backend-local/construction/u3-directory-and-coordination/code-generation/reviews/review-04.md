| R-08 | Major | supabase/migrations/20261038_notifications_hooks.sql > function family_archive (wrapper), with supabase/migrations/20261030_kernel_family.sql > family_archive_core and 20261037_notifications_functions.sql > reminder_plan, reminder_family_tasks | U3 promises that every writer that changes several tasks (family archive among them) takes the task row locks in ascending task id order (NFR3.8). The wrapper breaks this. The core first locks the tasks of the family's own places in ascending order. Only after that does the wrapper call reminder_plan_tasks on reminder_family_tasks, and reminder_plan opens with a row lock on each task (select ... for update). reminder_family_tasks returns every task on which the family is still an active recipient of a live job. With the recipient scope set to group (an allowed setting), that is every upcoming task of the family's groups, not only the tasks it held places on. So the wrapper takes locks on tasks with lower ids than ones it already holds. A concurrent swap exchange that locks the same two tasks in ascending order can then meet it in a cycle: the swap holds the lower task and waits for the higher one, the archive holds the higher one and waits for the lower one. The database aborts one of them with a deadlock error, which the gateway reports as an unexpected failure. The transaction is rolled back, so no data is damaged. U3's crossing archive-versus-swap test (kernel-swaps.test.ts) and the race test run with the default scope duty, where the recipient tasks are the family's own places and are already locked, so they cannot show this. I read the lock order in the code; I did not run the interleaving. | Make the archive take all the task locks it will need before the core touches any task, in one ascending pass over the union of the family's place tasks and its recipient tasks.
