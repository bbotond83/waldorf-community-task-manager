| R-08 | Major | supabase/migrations/20261038_notifications_hooks.sql > function family_archive (wrapper), with supabase/migrations/20261030_kernel_family.sql > family_archive_core and 20261037_notifications_functions.sql > reminder_plan, reminder_family_tasks | U3 promises that every writer that changes several tasks (family archive among them) takes the task row locks in ascending task id order (NFR3.8). The wrapper breaks this. The core first locks the tasks of the family's own places in ascending order. Only after that does the wrapper call reminder_plan_tasks on reminder_family_tasks, and reminder_plan opens with a row lock on each task (select ... for update). reminder_family_tasks returns every task on which the family is still an active recipient of a live job. With the recipient scope set to group (an allowed setting), that is every upcoming task of the family's groups, not only the tasks it held places on. So the wrapper takes locks on tasks with lower ids than ones it already holds. A concurrent swap exchange that locks the same two tasks in ascending order can then meet it in a cycle: the swap holds the lower task and waits for the higher one, the archive holds the higher one and waits for the lower one. The database aborts one of them with a deadlock error, which the gateway reports as an unexpected failure. The transaction is rolled back, so no data is damaged. U3's crossing archive-versus-swap test (kernel-swaps.test.ts) and the race test run with the default scope duty, where the recipient tasks are the family's own places and are already locked, so they cannot show this. ### Summary

U3's delivered behaviour holds after U4: all of U3's database, application and screen suites pass on the real stack, the U3 migrations are untouched, the renamed cores are not executable by any application role, and the wrappers keep the signatures, grants, pinned search path, error codes and replay behaviour (hooks run only for a fresh success, in the same transaction). Nothing I could check was weakened. The one real gap is that the family archive wrapper acquires task locks out of ascending order when reminders go to the whole group, which breaks the NFR3.8 lock-order guarantee that U3's tests only exercise with the default scope. That is one Major finding, within the allowed limit, so the verdict is READY, with that fix recommended before U3 is approved again.
