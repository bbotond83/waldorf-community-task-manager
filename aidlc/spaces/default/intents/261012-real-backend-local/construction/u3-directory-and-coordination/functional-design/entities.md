# Entities: U3 Directory, settings and coordination

The records U3 owns, in three parts that follow the owning blocks: Directory (people and structure), Settings, and Coordination (events, tasks, sign-ups and requests). Source: `components.md` (Entity Ownership), ADR-001 to ADR-013, requirements FR2.3 (link), FR2.8, FR3.4, FR4.1, FR4.3, FR4.4, FR5.1 to FR5.5, FR6.1, the confirmed answers Q1 to Q8 in `functional-design-questions.md`, and the existing modules and four running adapters. Conventions from U1 and U2 apply: uuid keys generated by the database, `organization_id` on every table, `version` on records that people change at the same time, UTC timestamps, no foreign keys across blocks (typed ids instead, checked by the named functions).

Placeholder tables: the first migration created `app_families` and `app_assignments` (with `scope_id` columns and policies) for the access tests, and U2's shipped functions still read them: the invitation create function and its stale-reservation replacement (family scope check), the session and scope helpers (family scope by `scope_id`), and the access-change functions. U3 therefore does not simply drop them. Its migrations first replace those function bodies with `create or replace` versions that read the new Family table instead (merged migrations are never edited). The replacement is exact: in U2's SQL a family's `scope_id` is the id of the family's group and is always passed as a group, so after U3 the group reach of a family is an active GroupMembership in a group where the actor holds a group admin grant (a family with several memberships is reached through any of them; with none, by super admins only); the audit group of a family-scoped event is the first group (lowest id) among the family's active memberships that the acting admin reaches, and null for a super admin or a family without membership; the group reach of an assignment is its task's group (the new Assignment has no group column of its own, so the access check joins to Task). The U2 functions rewritten for this are `invitation_create` and its stale-reservation replacement, `identity_can_manage_scope`, `identity_account_visible`, `grants_admin_read`, `identity_scope_group` and the family and assignment access checks in the access-change functions; U2's identity tests, including every group-admin case, are re-run against the new tables and must stay green, move the access tests that used the placeholders onto the new tables, and then drop both placeholder tables only when a catalogue check (like U2's BR2.22 check) shows no function body, policy, view or source file still names them; if the check finds a user, the drop is left out and the test names it. `app_import_runs` stays for U4. Cross-block links are typed ids: in particular the two Settings tables hold `organization_id` as a typed id and Task, Event and Assignment hold group, family and parent ids the same way. Audit follows U1: only role changes, approvals, imports and lifecycle actions are audited (U1 BR3.2), so U3's entities have no audit rows of their own.

Two deliberate changes against the old in-memory model, both from the domain design: a child no longer carries its own group; the family belongs to a group through GroupMembership (so "which tasks may this family take" is decided at family level). Contact details leave the parent record and live in their own table, ParentContact, so a policy can hide them as a whole (FR3.4).

entities:
  # ---------------- Directory ----------------
  - name: Organization
    owner: Directory
    description: "The school community; the top of every scope"
    attributes:
      - { name: id, type: uuid, required: true, unique: true, default: "database-generated" }
      - { name: name, type: text, required: true, constraints: "1 to 200 characters" }
      - { name: status, type: text, required: true, allowed: [active, archived], default: active }
      - { name: created_at, type: timestamp, required: true, default: "now (UTC)" }
    constraints:
      - "created only by the seed or the operator command; U3 screens read and rename it, they do not create organizations"

  - name: Parent

## Relationship Summary

- Organization has many SchoolYears, Families and Settings; a SchoolYear has many Groups.
- A Family has many Parents, Children and GroupMemberships; a Parent has at most one ParentContact and at most one Account link.
- A Group has many Events and Tasks; an Event has many Tasks; a Task has many Assignments; an Assignment has at most one open ChangeRequest and at most one ContributionNote.
- Cross-block references (Task to Group, Assignment to Family and Parent, Parent to Account) are typed ids checked inside the named functions, never database foreign keys (ADR-001).
