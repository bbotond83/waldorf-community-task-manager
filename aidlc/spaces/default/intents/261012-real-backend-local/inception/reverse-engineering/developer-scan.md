### 2. Runtime composition and every synthetic-mode dependency

**Config (`src/runtime/config.ts`)**
- `validateRuntimeConfig(env)` reads `APP_RUNTIME_MODE`: only `synthetic` or `production`, else `CONFIG_RUNTIME_MODE_INVALID`.
- Synthetic: `APP_SYNTHETIC_FIXTURE_VERSION` (regex, default `waldorf-local-v1`).
- Production: `APP_SESSION_SECRET` (min 32), `SUPABASE_URL` (https only, so `http://127.0.0.1:54321` is rejected), `SUPABASE_ANON_KEY` (min 20). Shape check only.
- Error codes: `CONFIG_RUNTIME_MODE_INVALID`, `CONFIG_SYNTHETIC_INVALID`, `CONFIG_PRODUCTION_INVALID`.

**Composition (`src/runtime/composition.ts`)**
- `composeRuntime(env=process.env)` is `async`, called on essentially every request (`app/page.tsx`, every `_lib/session.ts` and `_lib/facade.ts`, both API routes, actions). It dynamic-imports `synthetic/composition.ts` or `production/composition.ts`.
- The composition exposes only `application.authorization` (an `AuthorizationContract`) plus, in synthetic mode, `profiles`. There is no composition-level repository, database, clock, or facade registry; each page-support file builds its facade itself.
- Synthetic: `AuthorizationVersionPort.getCurrentVersion(subjectId)` reads `currentSyntheticActor(subjectId)?.authorizationVersion` (module-level Map).
- Production: stub, `getCurrentVersion: () => undefined` (so every authorize would return `invalidated`). `app/page.tsx` renders "Az éles hitelesítési kapcsolat még nincs összekötve" for production mode. Every `_lib/session.ts` and `_lib/facade.ts` returns `denied` / `undefined` when `mode !== "synthetic"`, so production mode currently serves no feature.

**Session (`src/runtime/session/session.ts`)**
- Cookie `waldorf_local_session`, HMAC-SHA256 over a base64url JSON payload `{profileId, authorizationVersion, issuedAt, nonce}`, `payload.signature`, max age 8 h, `httpOnly`, `sameSite: lax`, `secure` is passed in as `false` by every caller (hardcoded).
- Signing secret is a **hardcoded constant** `waldorf-local-synthetic-session-key-v1` in source; `APP_SESSION_SECRET` is validated in production config but never read by the session code.
- `profileId` doubles as `subjectId`; the token holds no user, family, or group; resolution does `getSyntheticProfile(profileId)` and `currentSyntheticActor(profileId)` and compares the stored authorization version, so version bump is the only revocation path. No server-side session record, no logout other than cookie deletion (`profileId=""` posted to `/api/synthetic/session`), no rotation, no per-session id.
- `SessionContext` (application) carries `subjectId`, `authorizationVersion`, `isActive`, `grants`, `roles`, `scopes`, `runtimeMode`, `isSynthetic`; `AuthorizationContract.authorize` rejects sessions whose `runtimeMode`/`isSynthetic` pair is inconsistent (`INVALID_SESSION_MODE`).

**Synthetic profiles (`src/runtime/synthetic/profiles.ts`, `access-state.ts`)**
- Exactly 4 profiles: `parent-local`, `kindergarten-teacher-local`, `group-admin-local`, `super-admin-local`, each with `authorizationVersion: 1`, home path and a per-profile navigation list (Hungarian labels). `syntheticProfileIdSchema` is a zod enum of those four.
- `access-state.ts` binds each profile to grants: parent -> family `family-boroka` (org `org-napsugar`); teacher -> groups `group-oak`, `group-sunflower` (org `org-waldorf-local`); group admin -> group `group-boroka` (org `org-napsugar`); super admin -> org `org-napsugar`. States live in a **module-level `Map`** (not on `globalThis`, unlike the other stores). Inference/risk: after a production build the reset route and the pages may hold different module copies (the other three stores carry a code comment about exactly this problem).
- Org ids are inconsistent across fixtures: teacher data uses `org-waldorf-local`, parent/admin use `org-napsugar`. `verification/fixtures.json` uses a third set (`family-fenyo`, `group-oak`).

### 3. Access model and migrations

**Migration 1: `supabase/migrations/20260806_access_rls.sql` (historical baseline)**
- Tables: `app_role_grants(id uuid pk, subject_id uuid, role text, scope_type text, scope_id uuid, organization_id uuid, revoked_at timestamptz)`, `app_authorization_versions(subject_id uuid pk, authorization_version int default 1)`, and four thin domain tables with only `id`, `organization_id`, `scope_id` (and `summary text` on audit): `app_families`, `app_assignments`, `app_import_runs`, `app_audit_events`.
- RLS enabled on all six; policies use `auth.uid()` (Supabase auth schema function), `has_active_scope`, `has_admin_scope` (roles `super_admin`, `kindergarten_admin`, `group_admin`).
- **Finding F1 (verified by executing it on a throwaway PostgreSQL 18.6):** the file fails to apply on real PostgreSQL. It aliases a table with the reserved word `grant` (`from app_role_grants grant`), giving `ERROR: syntax error at or near "grant"` for both `has_active_scope` and `has_admin_scope`; the dependent policies then fail with `function has_active_scope(uuid, uuid) does not exist`. The disposable test fixture (`tests/database/fixtures/current-role-baseline.sql`) re-creates the baseline with alias `g` instead, so the repo's database test never exercises the real file. In addition `tests/unit/current-role-references.test.ts` pins the file's SHA-256 (`a34b85b7…2449d`), so editing it breaks an existing test. It also needs `auth.uid()`, `auth` schema and roles `authenticated`, `anon`, which exist on hosted Supabase and are emulated only in the test fixture. The file name `20260806_access_rls.sql` has no time part (Supabase CLI filename convention is `<timestamp>_name.sql`; an 8-digit version parses, but note it).

**Migration 2: `supabase/migrations/20261006_current_roles.sql` (current roles)**
- Offline, transactional (`begin … commit`), locks `app_role_grants` and `app_authorization_versions` exclusively, **requires** `SET waldorf.authoritative_issuer_baseline = 'verified-v1'` on the connection or it raises `INCOMPATIBLE_SCHEMA`.
- Preflight validates column types and nullability, duplicate identities, no triggers, version default 1, role/scope pairs (`UNSUPPORTED_ROLE_OR_SCOPE`), version overflow.
- Converts `read_only_staff` -> `kindergarten_teacher` and `kindergarten_admin` -> `super_admin`, bumps versions, writes `app_role_conversion_evidence(operation_id, grant_id, subject_id, organization_id, original_role, current_role, outcome)`.
- Adds CHECK `current_role_scope` (`parent`+`family`; `group_admin`/`kindergarten_teacher`+`group`; `super_admin`+`organization` with `scope_id = organization_id`) and `positive_authorization_version`.
- Drops **every** existing policy on the seven owned tables and the old functions, then defines `authorization_version_for` (self only), `has_current_role_scope(role, org, scope_type, scope_id)`, `has_super_scope(org)`, `has_core_scope(org, group)`; grants execute to `authenticated` only; revokes insert/update/delete on grants, versions and evidence from `anon, authenticated` (grant writes are server-only).

- Not covered by any table or policy: school years, groups, children, parents/guardians and user profiles, tasks, events, task capacity, signups, swap and cancellation requests, approvals, notifications, reminder jobs and attempts, invitations, import preview/conflict/sheet registry, contribution notes, settings, recipients, lifecycle/retention holds, contact visibility fields, idempotency records, application evidence and event journal.

### 4. Authentication today

- **Where users and identities live:** nowhere persistent.
