### Verification of the points asked

1. **Lock order.** No cycle exists in any command I traced. Save and switch: family, schedule row, occurrences ascending (lines 804-868, 925-947). Mark done, undo, skip: holder family, then the occurrence only (lines 1066-1067, 1132-1133, 1202-1203). Daily check: owning family, schedule, occurrences ascending, and the notice call takes no family lock (lines 1317-1348). Removal apply: family, schedules ascending, occurrences ascending (lines 1420-1427). Because the occurrence commands never take the schedule row, no command locks an occurrence before its schedule. Races of mark or skip against switch-off or against a rota republish resolve safely: the later statement re-evaluates `status = 'open'` after the lock wait, and a deleted row gives `VERSION_CONFLICT`. The gap is the missing rota-week lock (Major row). The holder is re-read after locking, only where the caller's right depends on it (mark done always, undo by the marker; line 1020).
2. **Notice window (D-REL-1).** Correct. A run selects days 0 to 2 only when neither notice exists, and day 3 or more only when no overdue notice exists (lines 1344-1345). The kind is chosen from `v_days` alone, so one run never sends both and a due notice is never sent late. tests/database/recurring-check.test.ts lines 82-110 pin nine day-sequences, including `[3]`, `[0,3,4]`, `[2,3]`, `[0,0]` and `[-1]`, with queued email counts and the stored timestamps.
3. **D-REL-3, D-SEC-1, denied not empty, grants.** Flags and constraints match the design (lines 87-98, 1428-1433); tests/database/recurring-core.test.ts line 201 and line 451 cover both sides. Super admin: `mark` is only true for a group participant or the holder family, so a super admin without a parent record cannot mark; undo and skip use `manage` (lines 1005, 1124-1126, 1193); test at recurring-occurrences.test.ts line 574 covers all three owner kinds. Every read gives a `denied` envelope for no access, unknown id and other community alike; `recurring_my_occurrences` refuses a caller with no parent record rather than returning an empty list. Every new function appears in a `revoke all ... from public, anon, authenticated, service_role` statement (lines 117, 601, 960, 1228, 1375, 1452) followed by an explicit grant or none; the tables carry row-level security and no rights. Refusals use `platform_abort` / `platform_field_invalid` and are returned from the U3R00 handler. No existing business row is changed.
4. **Deviations.** (a) Accepted: no role may call `recurring_due_check`; the test at recurring-check.test.ts line 592 shows the service role gets 42501, and the registry test shows it runs through `timed_checks_run_system`. (b) Accepted: the account id is needed because a super admin may have no parent row (constraint lines 96-98); see the Minor row on removal. (c) Accepted: both extra reads check the caller themselves and are tested (recurring-core.test.ts lines 645-700). (d) Accepted: I compared the replacement with 20261050 lines 643-701; the only differences are the `detail` column and the extra `detail` key in the result; the grant stays service_role only and a test pins it. (e) See the Minor row; the code restarts per plan, tests pin it. (f) Accepted: the notice call is inside the schedule's sub-transaction, so a failing notice rolls the schedule back alone and the id goes to `detail`; the failure test is at recurring-check.test.ts lines 547-603. (g) Accepted: save derives `rota_weeks` from the owner kind (lines 847-848), consistent with the table check on line 54. (h) Matches BR144.2 ("lets the daily run create occurrences"); not pinned by a test (see Minor row). (j) See the Minor row. (l) Not accepted as evidence; see the Major row.
5. **Test quality and personal data.** The database tests assert state (rows, versions, audit counts, notice counts), and the race tests repeat 20 times in both orders. I ran the four integration files for the screens, pages, actor and actions in Vitest: 54 tests, all passed. I did not run the database tests, the browser specs or the 39-minute `npm run verify:local`; they need the local database stack, so the reported counts and coverage (92.61 / 86.61 / 94.02 / 94.03 against the 80/80/80 floor) are the agent's own and are not re-verified here. A scan of the unit's migration, source and test files found no email address or phone number; the seed titles are invented Hungarian duty names; the test ids are placeholder UUIDs.
6. **Traceability.** Every target in traceability.json exists. Most IDs are mapped by content rather than cited by name; the mismatches I could confirm by reading are the three in the Minor row above. NFR3.10 points at the authorization matrix, which carries the super-admin rows (checked in the diff) and is a data file, not a test.

### Summary

The unit is implementable and well tested: the notice window, the removed-parent flags, the super-admin asymmetry, grants and refusals all match the design, and no deadlock cycle exists. One Major gap should be weighed before approval: the rota-week holder race is not actually serialised against the real swap path, and its only test imitates the swap with a lock the real swap does not take. Five Minor points (undo flag, three traceability targets, the rota numbering reading, overdue age cap, account id kept on removal) can ride along.
