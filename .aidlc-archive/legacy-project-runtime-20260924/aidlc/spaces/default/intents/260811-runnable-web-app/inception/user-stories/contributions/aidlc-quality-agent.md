## Contribution

The delta set has the right quality intent: every story uses Given/When/Then, synthetic data is explicitly privacy-safe, direct UI/API denial is represented, revocation and field absence are named, browser evidence spans Chromium/Firefox/mobile Chrome plus recorded Safari smoke, and US-LR-07/09 correctly prevent simulated adapters from being reported as real Supabase, provider, scheduler, persistence, or Vercel evidence.

The draft is not yet uniformly executable as a pass/fail acceptance suite. Several criteria combine many independently failing behaviors into one `then` and delegate the expected result to an inherited story range, an unapproved FR-LR-14 matrix, or phrases such as “match,” “remain usable,” “actionable,” and “satisfy NFR-08.” Split or table-drive these into scenario-level assertions with an evidence ID, preconditions, observable UI/API result, protected-state invariant, and required evidence artifact. In particular:

- US-LR-04 and US-LR-06 should enumerate the inherited state transitions they claim to accept. A test must be able to distinguish denied/no-mutation, pending, success, conflict/invalidated, dependency failure, retry, and atomic recovery without interpreting “match US-01 through US-04” or “without partial success.” For denied and failed mutations, assert unchanged owned state, no unauthorized side effect, and only the permitted redacted audit outcome. For retryable operations, assert idempotency or the exact duplicate-prevention outcome.
- US-LR-07 should bind authorization evidence to versioned FR-LR-14 matrix row IDs. Minimum negative cases should explicitly include Parent → unrelated family; Read-only Staff → mutation/contact/profile/reason fields; Group Administrator → ungranted group; Kindergarten Administrator → super-admin governance; every role → forbidden direct API/object identifier; and immediate grant/session revocation on the next request, including stale navigation/cache. Each denial should assert generic status/body, absent sensitive fields, no resource-existence oracle, no state change, and privacy-safe logs/audit/screenshots.
- US-LR-03 and US-LR-08 need measurable accessibility evidence rather than “usable.” Assert one main landmark/H1, a functional skip link, deterministic keyboard focus order and restoration after profile switch, status/error announcements, no keyboard trap, 200% zoom without loss of content/action, and computed 44×44 CSS-pixel targets. Automated axe results cover only the stated serious/critical threshold; keyboard, zoom, focus, touch target, and Safari behavior require separately recorded checks.
- US-LR-08 should name the critical-flow manifest and its browser coverage matrix. Record browser/engine/version, viewport/device emulation, scenario IDs, result, timestamp, and evidence location. Chromium, Firefox, and mobile-Chrome emulation are automated CI evidence; Safari desktop and mobile Safari are real WebKit-environment smoke evidence, not inferred from Chromium emulation. A dated exception must name approver, scope, expiry, and residual risk; otherwise missing Safari evidence remains a release blocker.
- US-LR-01 should make “successful application response” and “actionable privacy-safe message” objective: expected command exit code, HTTP status/route, required Hungarian page marker, deterministic readiness/timeout behavior, validation error identifier, and absence of secret values. Unsupported Node/npm and each required environment-variable boundary should be separate cases.
- US-LR-02 should assert that production mode has neither selector markup nor selector endpoint/action and cannot activate a synthetic identity by crafted request. Profile switching should prove prior cookies/session/grants are cleared, authorization is recalculated server-side, and focus lands on a named element.
- US-LR-09 should define non-deployment evidence: no executable deploy workflow, no target credentials required, no staging/production network invocation, and a report that marks every Acceptance Evidence Matrix row as `PASS`, `FAIL`, `BLOCKED`, or `OUTSTANDING` separately for synthetic and linked-target execution.

Coverage is incomplete against the supplied requirements. FR-LR-03 domain composition has no explicit story acceptance criterion for the architecture/contract verification. NFR-LR-04's inherited two-second threshold is not asserted by a delta story, including dataset/profile, measurement start/end, percentile or repetition rule, and environment. NFR-LR-06's boundary/style constraints may remain engineering acceptance, but US-LR-08 should explicitly include the architecture tests/review and maintainability checks if they are release-gating. Add direct trace rows rather than relying on broad inherited references.

The INVEST statement should be qualified. US-LR-02 through US-LR-09 form a strict dependency chain, US-LR-08 depends on every prior story, and US-LR-06 spans several administrator products and lifecycle families. These are coherent acceptance epics, but not all are independently testable stories. Split US-LR-06 by Group/Kindergarten/Super Administrator or by bounded workflow, and treat US-LR-07/08/09 as cross-cutting acceptance gates with explicit manifests rather than claiming full independence.

Test-data evidence should define stable synthetic identifiers and deterministic factories for each role/scope/state, with no production-derived values. Add a scanner/assertion over fixtures, responses, logs, audit output, screenshots, and generated reports, but do not call that proof of real-target privacy or RLS. Real-target assertions must remain `OUTSTANDING` until executed against linked integrations, exactly as the requirements matrix states.

## Positions

- **Given/When/Then:** Retain BDD form, but require one observable behavior per scenario or a named data table; eliminate acceptance by vague cross-reference.
- **Authorization/privacy:** Every critical matrix boundary needs both allow and deny evidence at UI and API/object level, plus no-mutation, non-enumeration, redaction, and next-request revocation assertions.
- **Coverage:** Add explicit story coverage for FR-LR-03 and NFR-LR-04; make the requirement → story → scenario/evidence mapping machine-checkable.
- **Browser/accessibility:** Keep Chromium, Firefox, mobile Chrome, Safari desktop, and mobile Safari boundaries distinct; record versions and scenario IDs, and pair automated accessibility scans with manual/recorded keyboard, focus, zoom, touch-target, and Safari checks.
- **Synthetic versus real:** Synthetic adapters may prove application authorization, validation, state mapping, and redaction only. Supabase RLS/object access, persistence/transactions, scheduler/provider behavior, and Vercel deployment cannot pass until exercised against real linked targets.
- **Quality gate:** Release readiness requires all local commands and critical scenarios green, coverage at or above 80% for line/branch/function, no serious/critical accessibility violations in critical flows, no high/critical dependency or SAST findings, and no unapproved outstanding browser evidence.
