## Contribution

The current story set names the principal workflows, but its acceptance clauses are summary labels rather than independently executable Given/When/Then scenarios. To satisfy the inception testing guardrail and make the Standard-depth feature testable, retain the current story grouping but expand each story with observable success, denial, boundary, and error outcomes, plus traceability to the functional requirements below.

| Story | Testability gap | Minimum acceptance outcomes to add |
|---|---|---|
| US-01 | “linked duties display” and “primary-recipient rules” do not specify active/inactive links, action permissions, or delivery results. | Given two active linked parents, when either views an assignment, then both see it and may take permitted actions; given an unrelated parent, when requesting it through UI or API, then access is denied with no sensitive fields returned; given an authorized primary-recipient selection, when a reminder is scheduled, then only that active recipient is queued. (FR-02, FR-03) |
| US-02 | Atomic swaps, approvals, conflicts, and reminder recalculation are compressed into one clause. | Given two confirmed, conflict-free families, when both confirm a swap, then exactly the two assignments exchange in one transaction and both reminder queues are recalculated; given a conflict, capacity breach, incomplete confirmation, or an ineligible requester, then no assignment changes; given any other valid swap, then it remains pending until an in-scope administrator approves or rejects it. (FR-05) |
| US-03 | The schedule, timezone, recipient changes, duplicate suppression, retry, and accessibility requirements are absent. | Given a duty in Europe/Budapest, when it is scheduled, then Hungarian reminders are queued for 7 days and 24 hours before it; when the duty or recipient changes, then stale reminders are cancelled and duplicate active reminders are absent; when delivery fails, then retry and privacy-safe administrator status are recorded; the reminder content and associated parent flow meet the defined WCAG test scope. (FR-13, FR-14, NFR-03, NFR-04) |
| US-04 | It omits archive/restore and relevance/denial behavior by entity and role. | For every listed record type, given an authorized administrator, when creating, editing, archiving, or restoring it, then the change succeeds within the administrator’s scope; given a parent or out-of-scope administrator, when attempting the same action, then it is denied; given a parent view, then only records relevant to linked children/groups are returned. (FR-05a) |
| US-05 | “role-scoped” and “immediately” are not assertable; field-level visibility and audit evidence are missing. | Given each role/resource/field combination in the approved matrix, when the UI or REST API is used, then only allowed data/actions are returned; when role or scope is removed, then the next authenticated UI/API/data request is denied; sensitive data is absent from responses, logs, notifications, fixtures, and screenshots; privileged changes create redacted, access-controlled audit evidence. (FR-01, FR-03, NFR-01, NFR-07) |
| US-06 | “all 17 sheets migrate safely” lacks deterministic preview, conflict, idempotency, interruption, hostile-file, and recovery outcomes. | Given a supported workbook, when previewed, then every sheet and row type has a deterministic mapping result and ambiguous identities enter a review queue; when the immutable preview is approved, then commit is atomic; when the same or interrupted import is retried, then no duplicate entities are created and changed/already-imported rows are reported deterministically; unsupported or hostile input is rejected safely; the approved rollback/recovery drill restores verified service within one hour. (FR-08–FR-12a, NFR-06) |
| US-07 | The lifecycle policy is too broad to assert; sibling, grace-period, hold, and redaction cases are absent. | Given the last enrolled child leaves, when 30 days elapse without a hold, then eligible contact/profile fields and private notes are deleted, permitted history is anonymized, and only the redacted audit minimum remains; given another enrolled sibling or a recorded hold, then deletion is deferred according to policy; annual review actions and deletion outcomes are access-controlled and auditable. (FR-04, FR-15, NFR-02b–NFR-02h, NFR-07) |
| US-08 | “relevant schedules” does not define permitted fields or negative assertions. | Given read-only staff, when viewing relevant schedules, then only coordination display names and authorized schedule data are visible; when attempting contact, sensitive-profile, or unrelated-family access through UI or API, then it is denied and those fields are absent. (FR-03) |
| US-09 | This is an NFR epic, not an independently testable story, and needs measurable journeys. | Define the core parent/admin journey inventory; under the 30-family normal-load profile, each listed page/API response completes within 2 seconds; the agreed Chrome, Safari, Firefox, mobile Safari, and mobile Chrome matrix passes responsive checks; core flows pass automated and manual WCAG 2.2 AA-aligned checks; CI runs formatter, linter, type-check, tests, coverage at or above 80% line coverage, and security gates. (NFR-04–NFR-06a) |

Test design should use isolated factories/fixtures for families, linked parents, roles/scopes, import rows, assignments, and reminder queues; synthetic data only for performance. Use a unit-heavy suite for authorization and state-transition rules, integration tests for UI/API/data-access and import/reminder boundaries, and a small E2E set for parent coordination, admin approval, import recovery, lifecycle deletion, and read-only visibility. Each requirement above should appear in at least one story acceptance criterion so the later requirement-to-story-to-test traceability check has no orphaned migration, event-note, preservation, or locale requirement.

## Positions

- OBJECT: The present one-line acceptance clauses are not Given/When/Then scenarios and do not provide pass/fail conditions for independent automated or manual tests.
- OBJECT: US-04 through US-07 leave material requirements untraced, including event-note permissions (FR-07), preservation of imported maintenance/cleaning status (FR-06), cross-surface validation equivalence (FR-12), and Hungarian locale/search/phone standards (NFR-03). Add explicit criteria or narrowly scoped stories before approval.
- OBJECT: US-09 must be converted into measurable quality scenarios rather than the non-verifiable phrase “responsive core flows.”
